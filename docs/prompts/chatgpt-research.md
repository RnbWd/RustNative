# ChatGPT research prompt

I maintain RustNative, a reusable starter for building original, private personal apps. Each project chooses its primary platform and active targets from web, Android 16, iOS, iPadOS, and macOS. Some ideas may start from a familiar workflow, but the resulting apps should be distinct and extend well beyond it. I value native quality, privacy, and fast solo development. There is no requirement to share all UI or use Rust everywhere. Do not reverse engineer anything, extract assets, inspect private APIs, or clone a proprietary app. Study public source and documented APIs; recommend reuse only when licensing and practical integration support it.

Browse and cite current primary sources. I can attach RustNative's README, ARCHITECTURE.md, docs/PROJECT.md, docs/TOOLCHAIN.md, and .agents/skills if needed. Without them, treat this description as the baseline: a docs and tooling starter with per-project target selection, conventional web technologies, Compose, SwiftUI with AppKit where needed, and optional Rust and UniFFI. Separate what you verified from inference. Do not assume this starter already depends on any particular version.

1. **Architecture.** Compare ordinary web UI with no Rust initially, web UI calling Rust via WASM and wasm-bindgen, and a Rust backend such as Axum where private hosting and a server are justified. Compare Swift/SwiftUI and Kotlin/Compose with UniFFI against Tauri's WebView approach for installed apps; consider alternatives such as Dioxus, Slint, egui, or a native-only app only where they make a credible case. Distinguish browser deployment, native widgets, WebViews, and native device APIs. Compare accessibility, interaction quality, mobile plugin coverage, offline storage, private distribution, release packaging, build/debug complexity, and port cost. Recommend one default and give triggers for deviating. Show what stays portable in a web-to-native port, especially storage, async work, and platform effects.
2. **Rust libraries.** Build a shortlist by job, not a dependency bundle: data formats and errors, parsing/media, persistence and migrations, HTTP/TLS and async, browser/WASM interop, optional backend, and optional game work. For each serious candidate give the repo/crate, license, stable version checked and date, maintenance evidence, target-specific support and caveats, and when to skip it. Distinguish browser WASM from WASI and mobile/desktop native targets. Prefer libraries proven by app manifests, release workflows, or platform tests; distinguish advertised support from actual evidence.
3. **Projects to learn from.** Start with https://github.com/storytold/craft-anything. Use its public source to identify actual crate boundaries, portable code and dependencies useful for unrelated original apps. Separate standalone published crates, separately licensed components, and internal workspace crates that are not sensible dependencies. Skip its reverse-engineering workflows. Find Matthew Berman's verified GitHub presence through his own public links; inspect public Codex/Fable app and game demos where available. Verify authorship, model claims, Rust use, and whether source was actually published; say what you couldn't verify. Include a few other strong Rust app repos built from scratch, including recent popular AI-assisted projects if supported by evidence. Cite concrete manifests, source paths, release workflows, or tagged builds. Separate inspiration from a proven dependency and popularity from quality.
4. **Android 16 and Apple.** Android 16 is my only Android support/test baseline. Propose one compatible stable API 36 toolchain set: Studio, JDK, Gradle, AGP, Kotlin/Compose (including built-in Kotlin or compiler plugin as applicable), SDK/build tools, NDK, Rust/targets, cargo-ndk, and matching UniFFI/JNA if used. Explain minSdk vs targetSdk vs compileSdk, Android 16 minor SDKs, and how to validate ABI, release shrinking, and 16 KB page sizes on the real artifact. Give read-only inventory commands; distinguish required components from optional ones. Assume Xcode is already satisfactory; specify only what an Apple port would have to verify.
5. **Skills and prompts.** Find maintained public agent skills or instruction sets for Rust, browser apps, Android/Compose, Swift/SwiftUI, and cross-platform integration. Inspect the actual skill text and license. Compare their triggers, concrete workflows, release checks, portability, and maintenance burden to RustNative's local skills. Recommend what to adopt, adapt, or skip and whether to keep skills repo-local, offer a portable export, or distribute a package. Flag instructions that invoke external tools or install dependencies. Give a short kickoff prompt for a new web project and a later port prompt.

Return a concise Markdown report I can hand to a coding agent: recommended defaults and alternatives, library shortlist, verified example and skill links, Android compatibility matrix, and a prioritized list of proposed RustNative file changes. Use **adopt now / evaluate with a real feature / skip** to make the priorities actionable. Include one small experiment that could disprove the default. Cite specific source links next to claims, date version checks, and identify evidence gaps. Do not edit a repository or install anything during this research.
